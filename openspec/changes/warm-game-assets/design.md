## Context

- **Audio.** `lib/audio/player.ts` exposes a lazily created singleton `sound()`. Creating it also registers the
  window `pointerdown`/`keydown`/`touchend` listeners that call `unlock()` (Web Audio may only start from a user
  gesture). The first caller in practice is `Table.svelte`, so the listeners appear only once a table is on screen.
  The tap that got the player there (home → Play, lobby → Quick play) happened before, so the game starts with no
  audio context; the first cue only plays after a tap inside the game, and the cue files are only fetched then.
- **Tiles.** `lib/tiles.ts` maps a kind to `/tiles/...svg` under `apps/web/static/`. Each `<img>` in `Tile.svelte`
  fetches on first render, so a kind seen for the first time in a game shows an empty face until its file arrives.
  adapter-node serves `static/` with ETag but no `max-age`, so each new page load revalidates every file again.
  Classic is ~40 files (~0.9 MB), Slim 37 files (~190 KB, generated by `apps/web/scripts/slim-tiles.mjs`).
- Mobile, portrait, often on cellular: latency per request matters more than bytes.

## Goals / Non-Goals

**Goals:**
- Any gesture anywhere on the site unlocks audio; cue files are decoded before the game needs them.
- No tile ever renders without its artwork after warmup has had a moment of idle time.
- Repeat visits load tile artwork from cache with no network round trip.

**Non-Goals:**
- Playing sound before any gesture on a fresh page load (reload/reconnect into a game). The autoplay policy forbids
  it; no "tap to enable sound" prompt is added (minimal UI text).
- Service worker / offline caching of the whole app.
- Preloading the inactive tileset, rank icons, patterns or fonts.

## Decisions

1. **Arm audio from the root layout.** Split listener registration out of `sound()` into an exported `armSound()`
   (idempotent) called from `+layout.svelte` on mount; `sound()` keeps returning the shared player. This keeps the
   player testable through `PlayerDeps` and keeps `Table` untouched. Alternative: just call `sound()` in the
   layout — works, but hides a side effect behind a getter; an explicit name says what it does.
   The existing behaviour stays: `unlock()` creates the context and prefetches all non-null manifest entries;
   `setEnabled(true)` prefetches when already unlocked.

2. **Tile warmup module, driven by one effect in the root layout.** New `lib/tile-warmup.ts`:
   `warmTiles(set: Tileset)` collects the set's image URLs for all 34 kinds plus the red fives, creates an
   `HTMLImageElement` per URL, sets `decoding = 'async'` and `src`, then calls `img.decode().catch(() => {})`. Images
   are kept in a module-level `Map<TilesetId, HTMLImageElement[]>`, which both makes repeat calls no-ops and keeps the
   decoded bitmaps referenced. The layout runs `$effect(() => { const set = tileset(); idle(() => warmTiles(set)) })`
   where `idle` is `requestIdleCallback` with a `setTimeout` fallback (Safari lacks it). Because the layout is
   mounted on every page and `tileset()` is reactive, this covers home, lobby, direct game loads and tileset changes
   with one call site. Alternatives: `<link rel="preload">` in the head — fetches but does not decode, and would be
   static for one tileset; warming only on Table mount — too late for the first tiles on a fast match.

3. **Tile images become hashed Vite assets.** Move `static/tiles/**` to `src/lib/assets/tiles/**` and build the URL
   table with `import.meta.glob('./assets/tiles/**/*.svg', { query: '?url', import: 'default', eager: true })` in
   `tiles.ts`; `image(k, red)` looks the path up in that table. Built files land in `_app/immutable/assets/` with a
   content hash, which adapter-node already serves with `cache-control: public, max-age=31536000, immutable`.
   Vite inlines files under `assetsInlineLimit` (4 KB) as data URIs; that is fine (they need no request at all) but
   puts them in the JS chunk of `tiles.ts` — acceptable at these sizes. Alternative: keep `static/` and add cache
   headers — adapter-node serves static files before `handle` runs, so hooks cannot set them, and a long `max-age`
   without hashed names would serve stale art after an update.
   `slim-tiles.mjs` writes to the new folder; `LICENSE.md` (FluffyStuff CC0) moves with the classic set.
   Missing-file safety: a unit test asserts every kind × red × tileset resolves to a URL in the glob table, so a
   renamed file fails the test instead of rendering a broken image.

4. **No fairness impact.** Warmup loads the full public tileset regardless of game state, so its timing reveals
   nothing; audio prefetch loads every cue file, not ones tied to events.

## Risks / Trade-offs

- [Warmup competes with the page's own requests on slow links] → run it in idle time; Slim totals ~190 KB.
- [Classic tileset is ~0.9 MB to warm] → only the active tileset is warmed; Classic is opt-in.
- [Decoded bitmaps held in memory] → ~40 small SVGs; negligible next to the page. Only tilesets actually chosen are
  kept.
- [iOS may suspend the audio context in the background] → unchanged: the existing `visibilitychange` + next-gesture
  resume path stays.
- [Glob table typo / file rename] → the coverage unit test above.

## Migration Plan

Pure client change, deployable any time. Old `/tiles/*` URLs stop existing; nothing else references them (checked:
only `tiles.ts`, the slim generator and docs). Rollback = revert the commit.

## Open Questions

- None blocking. If a future landing page sees heavy non-player traffic, warmup could be gated to signed-in users
  or to the home/lobby routes; not needed now.
