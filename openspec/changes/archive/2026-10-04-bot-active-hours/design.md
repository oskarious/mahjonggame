## Context

Bot players (`apps/game-server/src/bots.ts`, `BotPool`) are `user` rows plus a `bot` row (`skill`, `active`). The pool
keeps their live state in memory (`idle` / `queued` / `busy`, `restUntil` 10–90 s after a game) and, once a second
(`tick`), summons idle bots for waiting humans and starts background games among idle bots (keeping `idleReserve`
idle). Every active bot is eligible at every hour, which gives them away. Settings live in `settings.ts` (stored in the
`setting` table, edited on `/admin`); types are in `@mahjong/protocol` `admin.ts`. The DB schema is owned by
`apps/web` migrations; `apps/game-server/src/db.ts` mirrors it.

## Goals / Non-Goals

**Goals:**
- Each bot behaves like one person in one place: a home time zone, sleep, work/school, a free-time window, and only
  part of that window actually spent playing, in sessions.
- Bot activity across the world overlaps so there is always *someone* online, with natural busy and quiet hours.
- Humans never wait longer because of schedules.
- Cheap: a few operations per bot per tick, no timers per bot.

**Non-Goals:**
- Simulating individual days in detail (holidays, sick days, vacations), or bots changing habits over time.
- Matching bot presence to measured human traffic (no analytics yet).
- Showing presence/"online now" to players (there is no such UI; this change adds none).
- Changing how bots play, think or pace inside a game.

## Decisions

### 1. Store a schedule per bot (`bot.schedule jsonb`), not derive it from the id
Shape (`BotSchedule`, in protocol `admin.ts` so the admin page can show it):
`{ tz: string; weekday: [startMin, endMin]; weekend: [startMin, endMin]; appetiteMin: number }` — minutes after local
midnight; `endMin` may exceed 1440 (a window running past midnight, e.g. 20:00–01:30 = `[1200, 1530]`).
- Generated by `schedule.ts#randomSchedule(random, settings)` when a bot is created; on `load()` bots with
  `schedule = null` get one and it is written back (so existing pools migrate without a data migration script).
- *Alternative:* hash the bot id into a schedule. No migration, but changing the region mix or generator would silently
  move every existing bot to another continent, and admins could not see or (later) edit it. Rejected.
- Migration `0004_bot_schedules` adds the nullable column; `REQUIRED_MIGRATION` moves to it and `db.ts` is updated.

### 2. Regions and windows
- Region mix as settings: `regions: { tz: string; weight: number }[]`, weighted towards Japan, riichi's home: Japan
  (`Asia/Tokyo`, ~55 %), rest of East Asia (Korea, China, Taiwan, ~10 %), Europe (several zones, ~20 %), Americas
  (~12 %), Oceania (~3 %). Busy hours therefore centre on the Japanese evening (~09–15 UTC). Each region entry is one IANA
  zone; validation checks the zone with `Intl.DateTimeFormat(undefined, { timeZone })` (throws on unknown zones).
- Local time via `Intl.DateTimeFormat('en-US', { timeZone, hourCycle: 'h23', weekday, hour, minute })`, with one cached
  formatter per zone — DST is handled for free.
- Window archetypes drawn per bot (weights inside the generator, not settings): *evening* (start 17–20 h, 4–7 h long;
  most bots), *late night* (start 21–23 h, past midnight), *daytime* (students/shift workers/retired: start 9–14 h),
  *split* is not modelled (one window per day type keeps it simple). Weekend window = weekday window widened earlier
  by 0–5 h (often starting around midday).
- Appetite drawn from `appetiteMin` range (default 90–240 min/day, skewed low: most play
  around 1.5–2 h, a few a lot).

### 3. Sessions from a daily intensity curve (non-homogeneous Poisson starts)
- Intensity in local minutes, `w(t)`: inside the window a raised-cosine bump (`0.35 + 0.65·sin(π·x)`, x = position in
  the window 0..1) — peak in the middle, still clearly positive at the edges; outside, `w` decays from the edge value
  exponentially with a 45 min scale ("spill"), cut to a floor of ~0.005 (very rare odd-hour sessions). The weekday or
  weekend window is chosen by the local day the window *started* on.
- Normalise so the expected sessions per day = `appetiteMin / meanSessionMin`; per-tick start probability for an
  offline bot = `rate·w(t)/∫w · Δt`. Computed every tick only for offline, active, idle bots (a multiply and a lookup;
  the curve integral is cached per bot).
- Session length: drawn from `sessionMin` range (default 20–150 min, log-uniform), giving `onlineUntil`. With
  in-session gaps from the existing `botRestMs` plus between-session gaps, bots look like people who play a few games,
  eat, come back.
- *Alternative:* a per-minute online probability (stateless "is online now?"). Simpler, but flickers: bots would drop
  in and out between consecutive games. Sessions give the bursts the user described. Chosen sessions.

### 4. Pool integration (`bots.ts`)
- `PoolBot` gains `schedule` and `onlineUntil: number` (0 = offline). `online(b, now) = !schedulesEnabled ||
  b.onlineUntil > now`.
- `tick()` gains `#sessions(now)` before summon/background: offline active idle bots may start a session;
  idle online bots past `onlineUntil` go offline. Busy/queued bots are never switched off mid-game — the check simply
  happens when they become idle again (`roomEnded` leaves `onlineUntil` as is, so an expired session makes them
  offline on the next tick).
- `#available(now)` adds `online`. Background games and `idleReserve` thereby count online bots only. Warm-up keeps
  using all idle active bots (new `#available(now, { anyHour: true })`).
- Summon fallback, in `#summon` when `#pickFor` finds nobody: if an offline idle active bot fits, start a session for
  it now (`onlineUntil = now + session length`) and enqueue it — this happens at the normal arrival time, so it is not
  a timing tell. Only when no bot fits online or offline does `growAfterMs` lead to `#grow`. At the pool max the
  existing "nearest idle bot anyway" path also ignores online state.
- Startup: after `load()`, each idle active bot starts a session with probability ≈ `rate·w(now)/∫w · meanSessionMin`
  (the steady-state chance of being mid-session), with a remaining length drawn uniformly from its session length.
  `seated()` from recovery sets `onlineUntil` to at least now + a short session so recovered bots count as online.

### 5. Pool size
At any moment only a fraction of bots is online (with the Japan-heavy mix and 90–240 min appetite maybe 10–15 % at the
quietest hour, 30–40 % in the Japanese evening). Default `botPoolMin` rises from 120 to 400 so ~30–100 bots are online at once, enough for `idleReserve`
(30, now counting online bots) plus background tables. The admin can tune it; growth still creates bots on demand.

### 6. Settings and admin
New `BotSettings` fields: `schedulesEnabled: boolean` (default true), `regions` (validated array, weights > 0, ≤ 30
entries, valid zones), `appetiteMin: [number, number]`, `sessionMin: [number, number]` (minutes, validated as ranges
with their own max). `mergeSettings` gets a branch for `regions`; the range validator is reused with a unit-aware max.
Changing `regions` only affects new bots (documented in the field comment). `AdminBot` gains `schedule`,
`online: boolean`; `counts` gains `online`, `offline` (`AdminBotState` keeps idle/resting/queued/busy/retired and adds
`offline` for idle bots outside a session). The admin page shows zone + local time + window in the bot list and the
new counts; no schedule editing UI in this change.

### 7. Fair play
Nothing new reaches clients: `PlayerInfo` is unchanged and online state is internal. The fallback summon uses the same
summon/arrival timing as a normal summon, so a human cannot tell a "woken" bot from an online one.

## Risks / Trade-offs

- [Too few online bots at quiet hours → background games stop and summons fall back often] → larger default pool,
  floor intensity, worldwide region mix; the offline fallback guarantees humans are served; admin can switch
  schedules off.
- [Fallback wakes the same bots repeatedly for a night owl human] → `#pickFor`'s preference for bots that didn't just
  play them applies to the offline fallback too; picked from the 3 closest.
- [Larger pool means more rows and growth by default] → 400 bots is trivial for memory/DB; ticks stay O(bots).
- [Invalid stored `regions` (e.g. a zone removed from the ICU data)] → `settingsFromStored` already falls back to
  defaults and logs; schedule generation skips zones that fail to format.
- [Ratings settle more slowly because fewer background games run at quiet hours] → warm-up ignores schedules; after
  warm-up this is accepted.
- [Tests depend on wall-clock time zones] → the pool takes `now`/`random` injections already; schedule maths take
  `(schedule, epochMs)` and are unit-tested with fixed instants; `TEST_CONFIG`/test settings turn schedules off for the
  existing pool tests.

## Migration Plan

1. Deploy web first (migration `0004_bot_schedules` runs on start; the column is nullable, old game servers ignore it).
2. Deploy the game server: it refuses to start without `0004`, generates schedules for existing bots on first load,
   and tops the pool up to the new minimum.
3. Rollback: set `schedulesEnabled = false` on `/admin` (instant, no deploy); a code rollback leaves the column unused.

## Open Questions

- Default region weights: start with the mix above; revisit once real human traffic by hour is known.
- Should an admin be able to edit a bot's schedule? Not in this change (read-only display).
