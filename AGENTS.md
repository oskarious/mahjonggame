# AGENTS.md

Guidance for coding agents (and humans) working in this repo. Keep it current when a decision changes.

## What this is

A lightweight, chess.com-style **riichi mahjong** site. Mobile **portrait, one-handed** play first; no gacha, no
anime characters, no fluff. Rules source: **EMA Riichi Rules 2025** (European Mahjong Association).

Current state: the rules engine, rule-based bots with measured Elo, a SvelteKit client where you play against
bots **in the browser**, and user accounts (Better Auth on Postgres). No server-side games, ratings or matchmaking yet
(see "Where this is going").

## Engine principles

- **Pure and deterministic.** `applyAction(state, action)` returns `{ state, events }` on a structuredClone; no I/O,
  no timers, no randomness except the seeded wall RNG in the state. A game is fully reproducible from
  `(rules, seed, actions[])` — that log is the plan for replays, crash recovery and storage.
- **Server-authoritative by design.** Clients only get `viewFor(state, seat)` and `redactEvent(e, seat)`. Never leak
  other hands, the wall, or who has call options (call windows wait for everyone; seats without options are skipped).
- **Rules are data.** Behaviour differences go into `RuleSet` flags. Presets: `EMA_2025` (strict) and `DEFAULT_RULES`
  (online default = EMA + east-only by default, red fives, bankruptcy, all abortive draws, riichi needs 1000 pts).
- **Engine TS constraints:** no enums/parameter properties (erasableSyntaxOnly, Node type stripping), import with
  `.ts` extensions, `structuredClone` is declared in `src/globals.d.ts` so the engine needs neither DOM nor Node types.
- Tenpai is decided by `waits()` (EMA: waiting only on a tile you hold all four of is noten), not by shanten alone.

## Testing conventions

- Scoring tests use `score(hand, opts)` from `test/helpers.ts`; the concealed string lists the winning tile last.
  The helper rejects hands that are not exactly 14 tiles (quads count 3) — it has caught several miscounted tests.
- Game scenarios use `rig({ hands, melds, discards, draws, riichi, turn, wallSize, ... })` + `play(state, steps)`.
  `play` auto-passes open call windows; pass `{ settle: false }` to inspect a window. Default dora indicator is 3z
  (dora = north) — avoid 4z in hands unless you want dora.
- Bots use randomness: pass a seeded `random` in tests (`seedRng` + `randomInt`), or games become non-reproducible.
- When a new test suite passes first time, sanity-check it by planting bugs (mutation check) — we did this for the
  rules and it found a real coverage gap.
- Where EMA differs from common (Tenhou/WRC) practice, tests pin EMA and also exercise the RuleSet flag.

## Bots

- `botAction(g, seat, { skill | profile, random })`. `botProfile(skill 0..1)` interpolates knobs: blunder rate,
  softmax noise, ukeire, value awareness, defense (genbutsu / suji / walls), push-fold, open-hand reading, call style,
  riichi style (dama with value), kans, placement awareness.
- Elo per skill is **measured**, not guessed: `scripts/calibrate.ts` plays East-only games and fits Bradley-Terry.
  Last run: ~1283 (skill 0) → ~1634 (skill 1); skill 0.45 is pinned to 1500 (arbitrary until humans are rated).
  0.9 and 1.0 plateau — raising the ceiling needs better play (look-ahead, reading), not more knobs.
- **Re-run calibration after any bot change** and commit the regenerated `bot-ratings.ts`.

## UI conventions (apps/web)

- **Portrait, one hand.** No square table: a round bar (round, honba/riichi sticks, dora as `indicator → dora`, wall
  count as tile outline + number), then **4 seat rows in turn order: right, across, left, you** (left = the only chii
  source, directly above you), then hints, action buttons, and the hand. Rows fill the height; pond tile size is
  computed to fit 18 discards per row and only shrinks if a pond grows past that.
- **Hand input:** the whole hand strip is one touch target (nearest tile wins). Press shows a magnifier; the magnifier
  also stays up for the selected tile. Tap selected tile again = discard. **Flick up = discard**; once the finger rises
  past 12 px the tile is locked (sideways drift can't switch tiles); 36 px arms the discard (magnifier turns gold).
  Off-turn presses only inspect.
- **Visual language (one meaning per cue):** gold glow = dora (incl. red fives); blue glow = matches the tile you are
  holding/selecting (only then — never automatic); raised tile = last discard / winning tile; green dot = suggested
  discard (hint level "full" only).
- **Minimal text.** Prefer visual cues over explanatory copy; no helper sentences, position labels, "x seen", etc.
  Keep only information-bearing text (yaku, scores, hint values the player opted into, button labels).
- Tiles show a Latin corner index (1-9 in suit colour, E/S/W/N, Wh/G/R); hidden on tiles < 16 px; toggle in settings.
- **Hint levels are server-decided** (`viewFor(..., { hints: 'off' | 'distance' | 'waits' | 'full' })`, default off),
  intended to depend on Elo; anything above the level is never sent.
- Dark neutral theme (tokens in `src/app.css`); no green felt.

## Gotchas we hit

- **Phone testing over the LAN is plain HTTP (not a secure context):** `crypto.randomUUID`, `navigator.clipboard`,
  service workers etc. don't exist there. Use `crypto.getRandomValues` (`$lib/random.ts`) and guard secure-only APIs.
  Do browser checks on `http://localhost:5173` (the LAN URL triggers permission prompts); prevent LAN-only breakage in code.
- **Vite dev server can serve stale/half-written modules on Windows** after rapid successive edits (symptoms: old UI,
  "does not provide an export named …", 500 Internal Error). `touch` the files or restart the dev server.
- Svelte 5: `let x: T | null = $state(null)` makes TS narrow `x` to `null` inside `$derived` closures — read it through
  an explicit type (`const p = x as T | null`).
- Screenshots in the browser pane can render as 2× crops; use a `scale` < 1 or measure via JS.
- **Better Auth caches a schema mismatch** found when `betterAuth()` is created and never rechecks after our own
  migrations. That is why hooks.server.ts imports `$lib/server/auth` only after migrating in `init`; don't import it
  statically from modules loaded at startup. After a Better Auth upgrade, a startup "schema mismatch" log means: add a
  migration.
- Auth in dev: no `BETTER_AUTH_URL`/`ORIGIN` → base URL is derived per request, limited to localhost and private LAN
  hosts, over HTTP (non-Secure cookies), so phone testing works. Production requires `ORIGIN`.
- Kysely 0.29: `Migrator`/`Migration` come from `kysely/migration`, not `kysely`.

## Deployment

- Hosted on a VPS with **Dokploy** (builds on push to GitHub `master`). App type: Dockerfile, build path `/`, context
  `.`, container port **3000**, HTTPS via Dokploy/Traefik.
- **Postgres** runs as a Dokploy database service on the same network. Web app env (required):
  `DATABASE_URL` (internal URL of that service), `BETTER_AUTH_SECRET` (≥ 32 random chars), `ORIGIN=https://<domain>`;
  also `ADDRESS_HEADER=X-Forwarded-For`, `XFF_DEPTH=1`. Migrations run on container start (fail → container exits).
- The runtime image contains `apps/web/build` (engine bundled) plus production `node_modules` (better-auth, pg,
  kysely); health check `GET /healthz` (does not touch the DB).
- No email server: no verification, password reset or email change. A forgotten password needs a manual DB fix.

## Where this is going (keep designs compatible)

- `apps/game-server`: Node + WebSocket rooms running the engine authoritatively (timers + time bank, bots fill empty
  seats at a target Elo via `skillForElo`, disconnect → bot takes over, reconnect resumes). Routed at `/ws` on the same
  domain; separate Dokploy app with its own Dockerfile and watch paths.
- Identity: accounts exist (user id is the key for everything). The game server authenticates the WS upgrade with
  `auth.api.getSession({ headers })` from the same cookie. Elo rating (plain Elo, new players start at 1000) comes
  with the game server: bot games in the browser can't produce trustworthy results. Postgres (Kysely) for ratings and
  game logs (seed + actions). The web client swaps `LocalGame` for a WS client with the same view/act shape.
- Debug features (show bots' hands, autoplay) should be hidden behind a flag in production.
